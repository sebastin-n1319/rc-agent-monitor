Cloud-Based Chiro EHR Integration

Our cloud-based Chiro EHR integration synchronizes data between the client's Jane account and the Adit application using the Adit Google Chrome extension.

The Chrome extension serves as the real-time synchronization agent. It monitors Create, Update and Delete (CRUD) operations performed in Jane and securely transmits these changes to Adit.

For real-time synchronization to work, the extension must be installed and connected on every workstation where practice staff, providers or other users access Jane and make changes. In cloud-based EHR environments, each computer or device used to access the EHR is called a workstation .

Real-Time Synchronization

When the extension is installed and connected on a workstation, patient, appointment and provider changes made in Jane from that workstation sync to Adit in real time.

For example, if a practice has 10 workstations but the extension is installed on only 5 , only changes made from those five are synced immediately. Changes from the other five are picked up later by Backup Sync.

Backup Synchronization

To keep data consistent, the integration includes a backup synchronization that finds and syncs any changes missed by real-time sync. It keeps Jane and Adit consistent but does not give immediate updates.

For Jane, backup sync reads the Jane audit logs and runs every 1 hour . To get complete, real-time data, the extension should still be installed on every workstation where users update Jane.

Known fix: new patients booked through Jane's own online booking portal were not syncing to Adit because of an audit-log mismatch. The fix runs on the hourly backup sync and was in QA (Nidhi) as of the 11 June review.

Most Important Issues for Support/QA

Issues fall into 5 major buckets:

1. Extension-related issues The most common problem is that the extension is not installed or connected on every workstation. Real-time sync works only where it is installed and active.

2. Backup-sync delay Backup Sync recovers missed changes hourly, not in real time. Users may see a mismatch between Jane and Adit until it runs.

4. Recall reminders Missing or misconfigured recall types and zero intervals caused duplicate reminders before the April 2026 fix. Check the recall configuration first.

5. Access and permissions The Adit user may lack Jane permission to view or manage shifts, or Adit cannot log in to the Jane account, which blocks shift sync and configuration checks.

Revolution Integration Background

BackupSync can fail for reasons outside Adit's direct control, including Revolution-side behavior or account/permission changes. Maintaining reliable synchronization therefore requires care around the following constraints:

• Query and retry activity - Revolution had previously raised concerns about retry/query activity. Do not recommend continuous retries for server-side failures without engineering approval.

• Permissions - A historical permission incident resulted in a warning from Revolution on 25 April and a .82 hotfix, followed by a further fix on 7 May (see Permissions and Access).

• Client account actions - Clients have blocked the Adit user after noticing query/report activity, and deleting or editing the Adit user in the Revolution Admin Panel has stopped BackupSync.

• Report vs. API syncing - The development team discussed moving a client from report-based syncing to API-based syncing after query/report activity was flagged.

As a result, the integration requires continuous monitoring, and any change to credentials, permissions, or the sync mechanism should be coordinated with engineering.

Unlike many cloud-based EHR platforms, Open Dental is traditionally known for its locally hosted / client-server architecture , although cloud-hosted deployment options are also available.

3. Open Dental architecture - How the system works technically

• API layer: Third-party applications communicate with Open Dental through its official REST API.

• eConnector: For Remote API access, an eConnector must run at the dental office and facilitate communication between Open Dental's hosted API service and the office.

• Third-party integration: Applications such as Adit can retrieve or update supported information through authorized API endpoints.

2. Integration Approach and Environments

Unlike Ascend (Chrome extension + RPA), Cloud 9 is an official partner API: no extension, no workstation agent, no scraping. All sync runs server-side from Adit to Cloud 9's web service.

Cloud 9 integration background

Access is granted by Planet DDS under signed agreements, and Cloud 9 can revoke it for misuse. Their guide states that any negative impact on clients or misuse of the APIs can lead to termination without warning, so every new cron or call frequency must respect the limits in Section 5.

Cloud 9's vendor lifecycle:

• MNDA signed before any documentation is received.

• Integration Agreement signed before sandbox access; it defines the integration type.

• Sandbox (alpha) testing ; the vendor is expected to be production-ready within 6 months (3-6 month extension needs Cloud 9 approval).

• Demo to the Cloud 9 integrations team; the service must be approved before going further.

• Beta with a small number of mutual live clients; target sign-off within about a month.

• Live relationship : the vendor may sell to any Cloud 9 ortho client.

SET (write-back) procedures need separate whitelisting, plus a demo to Cloud 9, before use.

Cloud 9 EHR structure

Each practice database has its own Client ID (GUID) ; the username and password are static per integration (shared across clients). A multi-location practice usually has one Client ID with several locations inside it, so Adit must filter by locGUIDs per Adit location.

Hierarchy used by the integration:

Client ID (database) → Location (locGUID) → Schedule View (schdvwGUID) → Schedule Column / chair (schdcolGUID) → Appointment

GUIDs are unique only within one Cloud 9 client database; Cloud 9 notes they can be shared across databases. Adit must key stored records on Client ID + GUID, never GUID alone.

4. Request and Response Format

All procedures, GET and SET, are an HTTP POST to GetData.ashx with an XML body and header Content-Type: application/xml ; the procedure name goes in <Procedure> .

Request

<?xml version="1.0" encoding="utf-8" ?> <GetDataRequest xmlns="http://schemas.practica.ws/cloud9/partners/" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"> <ClientID>[Cloud9 Client GUID]</ClientID> <UserName>[Partner UserName]</UserName> <Password>[Partner Password]</Password> <Procedure>GetAppointmentListSince</Procedure> <Parameters> <dtSince>03/31/2026 00:00:00</dtSince> <pageIndex>1</pageIndex> <pageSize>1000</pageSize> <locGUIDs>[locGUID]</locGUIDs> </Parameters> </GetDataRequest>

Response

<GetDataResponse xmlns="http://schemas.practica.ws/cloud9/partners/"> <ResponseStatus>Success</ResponseStatus> <Records> <Record> ...field tags... </Record> </Records> </GetDataResponse>

On error, ResponseStatus is Error with ErrorCode and ErrorMessage (Section 18). SET procedures return a single <Result> string such as Patient Added: <patGUID> or Appointment GUID Added: <apptGUID> ; Adit must parse the GUID out of that text.

Data formats and parsing rules

Type | Format
bit | 1 (true) / 0 (false)
date / datetime | 12/30/1999 12:00:00 AM (US format, 12-hour clock)
uniqueidentifier, char, varchar, nvarchar (IDs) | GUID, e.g. [id]
int, tinyint, money | Numeric; money as decimal
Null value | <dtBirthdate xsi:nil="true" />

• Pagination: paginated calls need pageIndex (default 1) and pageSize (max 1000). Loop until a page returns fewer rows than pageSize .

• List parameters: separators differ by procedure: locGUIDs on the appointment lists use , ; most other GUID lists use | . Check each procedure.

• Duplicate rows: several GETs repeat a record per address or contact row (e.g. GetAppointmentListByDate repeats AppointmentGUID when the patient has multiple addresses). De-duplicate on the primary GUID before upsert.

• Time zones: GetLocations returns each location's TimeZone ; convert appointment times using it, never the server's zone.

Overview

• It must be configured and validated location by location before regular cron synchronization starts.

• Times are typical cycle intervals, not guarantees; a change made just after a cycle starts lands on the next cycle.

17. Online Scheduling (New Patient): Adit → EHR

Purpose

A new-patient booking from the Adit booking link needs two whitelisted SET calls in Cloud 9: SetPatient creates the patient, then SetAppointment books the slot. Patients created in Cloud 9 can never be deleted, so the duplicate check before SetPatient is mandatory.

Cloud 9 Setup Required

• A patient status with code NEW (otherwise SetPatient fails).

• A contact info type Home if a phone number is sent.

• Schedule templates covering the bookable hours, and appointment types with Allow Online Scheduling checked.

• SetAppointment and SetPatient whitelisted (plus SetPatientDemographicInfo , SetPerson , SetPersonRelationship if used), with daytime access per the allow-list.

Four fields are required to create a new patient: First Name, Last Name, Location and Provider (Orthodontist).

Online Scheduling Flow

Show Slots (GetOnlineReservations) ↓ Check for Existing Patient (GetPortalPatientLookup) ↓ Resolve Responsible Party (SetPerson if needed) ↓ Create Patient (SetPatient) ↓ Fix Contact Details (SetPatientDemographicInfo) ↓ Book Appointment (SetAppointment) ↓ Verify (GetPatientAppointments)

Booking Sequence

• Show slots. GetOnlineReservations with the mapped schdvwGUIDs and OS-enabled appttypGUIDs (≤ 28 weeks). Each slot returns StartTime , ScheduleViewGUID , ScheduleColumn , Minutes and LocationGUID .

• Check for an existing patient. GetPortalPatientLookup by last name, first name (match on birthdate too) or, from cached data, GetPatientList . Existing patient → skip to step 6.

• Resolve the responsible party (minor or other payer). Look up the parent with GetPortalPatientLookup ( lookupByPatient = 0) or GetIsFamilyPartyList . If none exists, create them with SetPerson and keep the returned persGUID .

• Create the patient. SetPatient with first name, last name, providerGUID (orthodontist from GetEmployees ), locationGUID , and optional birthdate, address (2-letter state), phone, gender (Male / Female), persGUIDRelated + reltypGUID . Parse patGUID from Patient Added: <GUID> .

Eyefinity Integration Background

Eyefinity sync depends on Eyefinity’s web application rather than an official API, so changes outside Adit’s direct control can interrupt synchronization. Maintaining reliable sync requires care around the following constraints:

• No official API - Adit reads Eyefinity’s internal endpoints and server-rendered PDF reports. A change to Eyefinity screens or report layouts can break sync or report parsing without notice.

• Appointment-date data - Eyefinity returns data by appointment date, not by last-updated date, so BackupSync re-reads a date window and uses reports to find changed patients instead of a change feed.

• Credentials - BackupSync logs in with the client’s stored Eyefinity credentials. Adit’s stored password takes priority, and a rotation flow can reset the password when required. Rejected credentials stop all BackupSync activity.

• Volume - Clients can have 150-200 appointments a week, and PA sync makes about 30 calls per patient, so BackupSync runs only once or twice a day.

As a result, the integration requires continuous monitoring, and any change to credentials, permissions, or the sync mechanism should be coordinated with engineering.

Backup Synchronization (BackupSync)

BackupSync runs on Adit-managed VMs as one scheduled job per location, once or twice a day. It now calls Eyefinity directly over HTTP instead of driving a Puppeteer browser.

Key Points:

• Each run logs in with the client’s stored credentials; if they are rejected, nothing syncs until they are fixed.

• Modules run in a fixed order: Appointment, Order, Recall Types Master, Appointment Type, Provider, Patient Recalls (Mondays), Patient, PA Report, PA Insurance Payments, Extension Log.

• A failure in one module stops the remaining modules for that location for that run.

• Windows: appointments from 2 days back to 14 days ahead; orders from the last 14 days onward; patients added or updated that day.

• PA modules run only when the location is flagged PA-enabled; otherwise they are skipped without an error.

• The Extension Log step records a “last backup sync” heartbeat in Adit at the end of every run.

Appointment Sync

Real-Time Appointment Synchronization (Eyefinity Scheduler → Adit)

Appointment changes made in the Eyefinity Scheduler sync to Adit in near real time through the Adit Chrome extension .

Key points:

• Real-time sync works only on workstations where the extension is installed and connected .

• Without the extension, appointment changes are not synced in real time; they appear in Adit after the next Backup Sync .

• Appointments booked in Adit (Scheduler, OS, AI Front Desk) are written to Eyefinity within about 5 minutes .

• Backup Sync re-reads appointments from 2 days in the past to 14 days in the future , plus block-outs, vacations and holidays.

Synchronization details:

• Real-time sync source: Eyefinity calls captured by the Adit Chrome extension.

• Status logic: Checked Out = Completed by default, unless the location has its own status mapping (see Status mapping).

Limitations and troubleshooting

Most Eyefinity issues fall into five buckets, matching the support buckets used for Curve.

• Extension coverage: real-time sync works only where the extension is installed, logged in and connected, and the Eyefinity session is active.

Dentrix Ascend Integration Background

Initially, Adit had an official integration partnership with Dentrix Ascend. Following the end of that partnership, we transitioned to an RPA-based integration approach that relies on UI automation and API scraping instead of the official integration.

Since then, maintaining the integration has been an ongoing challenge. Dentrix Ascend regularly introduces security enhancements and anti-automation measures that can interfere with our synchronization process. Over time, these measures have included detection based on:

• References to the Adit application.

• Source IP addresses.

• High request volumes or excessive server load generated by automated activities.

• Additional bot-detection and security mechanisms designed to restrict non-official integrations.

As a result, the integration requires continuous monitoring, maintenance, and periodic updates to ensure compatibility with changes introduced by Dentrix Ascend and to maintain reliable synchronization between the EHR and the Adit application.

Recare Data

Recare (also referred to as Recall ) is a scheduled follow-up date used to remind patients about future treatment or preventive care. It is not an actual appointment date , but a tentative date established to indicate when the patient is due to return to the practice.

For example, if a patient requires a Prophy (Prophylaxis) treatment every six months, the practice creates a Prophy Recall with the appropriate recall interval based on the practice's configured preferences. When the recall due date approaches, the patient can be contacted to schedule the actual appointment.

Recare Data in Adit

Adit processes recare data primarily for the following modules:

• Recall Reminders

The Recall Reminders feature helps practices maintain patient retention and maximize production by ensuring that patients receive reminders when they become due for their recall visits.

Practices often create recall entries in the EHR but may forget to contact patients. Without timely reminders, patients may not schedule their follow-up appointments, resulting in missed treatment opportunities and lost production.

Adit addresses this by:

• Retrieving recall due dates from the integrated EHR.

• Identifying patients whose recalls are due or upcoming.

• Automatically sending recall reminders based on the configured reminder schedule.

This helps practices improve appointment scheduling, increase patient compliance, and reduce missed recall opportunities.

For Dentrix Ascend , Adit retrieves the recall master data from the Recare Master configuration.

Navigation Path:

Settings → Patient Care → Recare

The Recare Master defines the available recall types (such as Prophy, Periodic Exam, etc.) along with their associated recall intervals. Adit uses this information to identify the appropriate recall due dates and process recall reminders accordingly.

• Recall Report

The Recall Report enables practices to identify patients who are due for a recall within a selected month and monitor the status of their follow-up appointments. The report provides visibility into which patients have already scheduled their recall appointments and which patients are still pending scheduling.

For patients who are due for a recall but do not have an upcoming appointment, the report allows practice staff to proactively contact them via phone or text message to encourage them to schedule their visit. This helps improve patient retention, increase treatment compliance, and ok minimize missed recall opportunities.

Additionally, the Recall Report provides insights into the effectiveness of Adit's automated recall reminder system by showing how successfully recall reminders are converted into scheduled appointments.

Integration Architecture: Workstation Sync, Backup Sync, and Future Improvements

The integration keeps Curve and Adit data consistent in both directions using exactly two sync types: Real-Time Sync and Backup Sync.

Real-Time Sync

• The workstation (the Adit Chrome extension) is connected to both Curve and Adit.

• Curve → Adit: whenever something is created, updated or deleted in Curve, the workstation captures it and updates Adit in real time.

• Adit → Curve: changes made in Adit are picked up by a cron job within 5 minutes, and the workstation updates them in Curve.

• The workstation must be connected on every system the client uses to access Curve . Changes made on a system without a connected workstation are not synced in real time.

Backup Sync (Current Approach)

• Backup Sync acts as a secondary synchronization mechanism to keep data consistent between Curve and Adit.

• Backup Sync generates reports at specific intervals to identify data that needs to be synchronized.

• Based on these reports, data is synchronized in both directions: Curve to Adit and Adit to Curve.

• Currently, Backup Sync for all clients runs on Adit-managed virtual machines (VMs).

• This process helps recover data that may have been missed by workstation-based Real-Time Sync and supports synchronization between both systems.

Future Approach: Adit Sync App

• Adit is developing a dedicated Adit Sync App that will run on the client's computer.

• The goal is to make synchronization more feasible and improve the integration's capabilities, including real-time synchronization.

• Status: This app is currently under development and is not yet part of the live integration.

Synchronization

Types of Synchronization

The Curve-Adit integration uses three main types of synchronization:

1. Initial Sync: Synchronizes the existing data from Curve into Adit when a location is first connected.

2. Real-Time Sync: Synchronizes changes made in Curve to Adit through the Chrome extension installed on each workstation.

3. Backup Sync: Synchronizes data between Curve and Adit at scheduled intervals to recover missed changes and maintain data consistency.

Initial Sync

Initial Sync is performed when a Curve location is connected to Adit for the first time. Its purpose is to bring the existing data from Curve into Adit so that both systems have the required data to begin synchronization.

How It Works

• Initial Sync is triggered during the initial location setup and connection process.

• It imports existing data from Curve into Adit.

• Once the initial synchronization is completed, ongoing data synchronization is handled through Real-Time Sync and Backup Sync.

• Data covered: Providers, appointments, patients, operatories, Practice Analytics (PA), etc.

• Execution process and typical duration: Based on client's data volume.

Real-Time Sync

Real-Time Sync synchronizes changes made in Curve to Adit through the Adit Chrome extension installed on each workstation. Whenever a user performs a Create, Update, or Delete (CRUD) operation in Curve from a workstation where the extension is installed, logged in, and connected, the extension captures the activity and synchronizes the relevant data with Adit in real time.

When these situations occur, the affected changes may not be synchronized immediately and may need to be recovered through Backup Sync.

Backup Sync

Backup Sync is the secondary synchronization mechanism used to maintain data consistency between Curve and Adit. While Real-Time Sync depends on the Chrome extension installed on individual workstations, Backup Sync runs independently on Adit-managed virtual machines (VMs).

How Backup Sync Works

• The system generates reports at specific intervals to identify data that needs to be synchronized.

• Based on the generated reports, the system identifies relevant changes and synchronizes data between Curve and Adit.

• Bidirectional Support: Supports synchronization in both directions: Curve → Adit and Adit → Curve.

• Data Recovery: Helps recover changes that were missed during Real-Time Sync due to disconnected extensions, unavailable workstations, or temporary synchronization failures.

Permanent Location Mapping (PLM)

Curve uses Permanent Location Mapping (PLM) to ensure that data is synchronized with the correct Adit location, regardless of the location selected on the workstation. During initial setup, each Curve location is mapped to its corresponding Adit location using three identifiers:

1. Client ID

2. Client Name

3. Location URL

Once the mapping is established, the integration uses these identifiers to identify the correct location for synchronization:

• Step 1: When a user changes the location in Curve, the location-change event is received by the Adit service.

• Step 2: The service identifies the corresponding Adit location using the mapped Client ID, Client Name, and Location URL.

• Step 3: Data is then synchronized with the correct Adit location based on this permanent mapping. (The location selected in the workstation extension is part of the older mapping logic and does not determine the synchronization destination under the current PLM implementation.)

PLM Practical Example & Key Takeaway Example: Suppose a practice has three locations: A, B, and C. Even if the workstation extension has Location A selected, when the user switches to Location B in Curve, the Adit service identifies Location B through PLM and synchronizes the data with the corresponding Adit location. Key Point: PLM ensures that synchronization is based on the permanent mapping between Curve and Adit locations, rather than the location selected in the workstation extension.

Patient and Appointment Location Handling

• Location A Creation: When a patient is created in Location A, the patient is synchronized to Location A in Adit.

• Cross-Location Appointment: If an appointment for that patient is created in Location B, the appointment and associated patient data are synchronized to Location B as well.

• Multi-Location Presence: As a result, the same patient can exist in multiple Adit locations if they have activity across those locations.

• Recall Synchronization Logic: Recall synchronization follows separate location-selection logic: the patient's preferred location is checked first, followed by their next appointment. The next appointment is searched across the entire organization. If an upcoming appointment exists before the recall date, the recall is not sent.

Recare Data

Recare (also referred to as Recall ) is a scheduled follow-up date used to remind patients about future treatment or preventive care. It is not an actual appointment date , but a tentative date established to indicate when the patient is due to return to the practice.

Recare Data in Adit

Adit processes recare data primarily for the following modules:

1.Recall Reminders

2.Recall Report

The Recall Reminders feature helps practices maintain patient retention and maximize production by ensuring that patients receive reminders when they become due for their recall visits.

Practices often create recall entries in the EHR but may forget to contact patients. Without timely reminders, patients may not schedule their follow-up appointments, resulting in missed treatment opportunities and lost production.

Adit addresses this by:

• Retrieving recall due dates from the integrated EHR.

• Identifying patients whose recalls are due or upcoming.

• Automatically sending recall reminders based on the configured reminder schedule.

This helps practices improve appointment scheduling, increase patient compliance, and reduce missed recall opportunities.

The Recall Report enables practices to identify patients who are due for a recall within a selected month and monitor the status of their follow-up appointments. The report provides visibility into which patients have already scheduled their recall appointments and which patients are still pending scheduling.

For patients who are due for a recall but do not have an upcoming appointment, the report allows practice staff to proactively contact them via phone or text message to encourage them to schedule their visit. This helps improve patient retention, increase treatment compliance, and to minimize missed recall opportunities.

Additionally, the Recall Report provides insights into the effectiveness of Adit's automated recall reminder system by showing how successfully recall reminders are converted into scheduled appointments.

Most important issues for Support/QA

The issues fall into 5 major buckets:

1. Extension-related issues

Real-time sync works only on workstations where the Adit for Chrome - CV extension is installed, logged in and connected. A logged-out extension, an expired Curve session, a closed browser or a disabled extension stops real-time capture on that workstation.

2. Backup Sync delay

Backup Sync recovers missed changes from reports generated at intervals on Adit-managed VMs, so Curve and Adit may not match until it runs (every two hours for the Patient Card).

3. Adit → Curve delay

Changes made in Adit are picked up by a cron job within 5 minutes and written to Curve by a connected workstation, so they are not instant.

4. Location mapping

Data is routed by Permanent Location Mapping (Client ID, Client Name and Location URL), not by the location selected in the extension. A patient can appear in several Adit locations, and recall reminders follow a separate location logic.

5. Data that does not sync or depends on prerequisites

Medication cannot be synced from Curve. Patient notes sync only when the Practice Analytics database tables and stored procedures are in place.

Cloud-Based Dental EHR Integration

Our cloud-based Dental EHR integration synchronizes data between the client's Denticon EHR system and the Adit application using Denticon's official API . Synchronization is triggered through Adit sync APIs hosted on betaplanetddssyncapi.adit.com , and each API runs for a specific Adit Location ID .

Unlike the Dentrix Ascend integration, which depends on a Google Chrome extension and RPA (Puppeteer) automation, Denticon data is exchanged through supported API endpoints. The only module that still relies on the Chrome Extension is Recall Type Master data, because Denticon does not provide an official endpoint for it.

In Denticon, each client is identified by two values: the PGID (practice group) and the OID (office/location). Every Adit location must be mapped to the correct Denticon location before any data can sync.

Direction | Data Covered

Denticon Integration Background

Denticon is a cloud-based EHR provided by Planet DDS. Adit integrates with Denticon through its official API using a PDDS subscription key and OAuth-style client credentials (client ID and client secret). Because the integration uses supported endpoints, it is not exposed to the bot-detection and anti-automation measures that affect the Dentrix Ascend RPA integration.

The main limitation is coverage: some data, such as Provider Hours, Operatory Hours and Recall Type Master, has no official endpoint. Provider and operatory hours are not synchronized, and Recall Type Master is synchronized through the Chrome Extension and the existing build sync process.

Cloud-Based Chiropractic EHR Integration

Our ChiroTouch Cloud integration synchronizes data between the client's EHR (practice.chirotouch.com) and the Adit application using a Google Chrome extension and a headless desktop app . There is no official ChiroTouch partner API, webhook or change feed; both runtimes reuse the practice's own logged-in ChiroTouch session and call the same private APIs the EHR web app uses.

Runtime | What it does | Direction
Chrome extension "Adit for Chrome - CT" (Manifest V3, version 8.0.0.13 ) | Watches the EHR tab and captures appointment, patient, blockout, alert and charge changes as staff make them; receives Adit socket events | EHR → Adit (real time); Adit Pay and manual patient sync from Adit
Desktop app (headless Node) | Runs scheduled pollers that write Adit data into the EHR every 15 minutes | Adit → EHR

The Chrome extension is the real-time synchronization agent. It captures Create, Update and Delete operations performed in the ChiroTouch web app and sends them to Adit.

For real-time synchronization to work, the extension must be installed on every workstation (each computer or device used to access the EHR) where staff, providers or other users change data.

How to install the Adit Extension?

• Go to the Chrome Web Store page for Adit for Chrome - CT (store URL to be added) .

• Click Add to Chrome .

• When the extension popup appears, click Add Extension .

• Optional: pin the extension so connection / disconnection is easy to see. The badge turns green, yellow or red based on the EHR and Adit session.

• Log in with Adit credentials in the extension and select the location.

• Make sure ChiroTouch is open and logged in, and wait for the extension to show connected.

Real-Time Synchronization

When the extension is installed on a workstation, changes made in the ChiroTouch tab on that workstation sync to Adit in real time, within seconds.

For example, if a practice has 10 workstations but the extension is installed on only 5 , only changes made on those five sync immediately. Changes made on the other five are not captured.

Important for ChiroTouch: the extension currently has no workstation gate on captured changes , so every browser with an open EHR tab and the extension sends events. Only Adit socket events (Adit Pay, manual patient sync) are limited to the primary workstation .

ChiroTouch Cloud Integration Background

Adit has no official integration partnership or API contract with ChiroTouch Cloud. Instead, a client-side agent rides on the practice's own logged-in session:

• It reuses the EHR web app's own token from browser storage.

• It intercepts the EHR page's own API calls to detect changes.

• It can scrape the EHR audit-log report to discover deletions (currently disabled).

Recent work (2026) added Online Scheduling v3, practice analytics (PA) sync, an MVC-style backup sync, the desktop app, a treatment-plan feature, manual patient sync and a WebSocket ("gsocket") push channel. Latest commit: 0a85302 "latest build with gsocket" (2026-11-05).

What it solves:

• Keeps Adit's copy of practice data current (patients, appointments, blockouts and, when enabled, providers, rooms, appointment types, tags and analytics), which Adit engagement, online scheduling and analytics depend on.

• Writes Adit actions back to the EHR: bookings, confirmations, Adit Pay payments, forms / PDFs, notes and patients.

Because it depends on the ChiroTouch web app's private APIs and browser storage, the integration needs ongoing monitoring: changes ChiroTouch makes to its URLs, storage keys or API rules can break sync without warning.

ChiroTouch Cloud EHR Structure

ChiroTouch Cloud is a single web app at https://practice.chirotouch.com . Each practice is a tenant , and every API call is scoped to that tenant ( /tenants/{tenantId}/... ).

• Login: users sign in through AWS Cognito (us-east-1). The resulting user session token is what the integration uses; there is no long-lived integration credential. If the user logs out or the tab closes, sync stops.

• Locations: a tenant can have several locations. The Adit location is mapped to one EHR location ( ehrLocation ); appointment and blockout events from other locations are dropped.

• Patients have no mandatory location. When a patient's preferred location is empty, the integration infers it from the latest past or next future appointment; patients with no appointments sync to every Adit location.

• Time zone is read from EHR browser storage (falls back to the tenant registry, then America/New_York).

• MFA may apply to Cognito logins, which can block the unattended desktop app.

Patient Information Synchronization

Patients sync EHR → Adit in real time when staff create or edit a patient, check a patient out, open the patient's insurance, open charges or payments screens, or save encounter charges. Adit can also request a one-patient refresh ( manual patient sync ) through the socket. Patients sync Adit → EHR every 15 minutes through the desktop app (approved patients and patient forms).

How the patient is found: the integration does not use the EHR id directly. It waits about 3 seconds , then searches ChiroTouch by name + MRN and takes the first match, so patients with similar names can be mismatched.

Demographics

The sync sends the full ChiroTouch patient record, including:

• First and last name

• Mobile, home and work phone

• Email address

• Date of birth and sex

• Address

• Preferred provider and preferred location

• Other standard demographic details

Adit also receives derived fields: first visit date, last appointment (last 6 months, not deleted / rescheduled / canceled), upcoming appointment, and patient type ("existing" if any appointment is Checked-Out, else "new").

Related Patients

Active guarantors linked to the patient are synced as relationships. When Adit creates a guarantor (Online Scheduling v3, currently disabled), the relationship is always set to "Other".

Emergency Contacts

The first emergency contact is synced to Adit. When a patient form updates emergency contacts, all existing contacts are deleted and recreated in ChiroTouch.

Insurance

• EHR → Adit: the patient's insurance is included in the patient sync.

• Adit → EHR (patient forms): the payer is matched by payer name + alias . An existing Primary or Secondary plan is deactivated and a new plan created.

Balances and Aging

Each patient sync includes the balance, amount to collect, and aging buckets (30 / 60 / 90 / over 90 days, by date of service), plus first and last transaction dates from the running ledger.

Medical Alerts and Patient Notes

ChiroTouch stores patient notes as patient alerts .

• EHR → Adit: a new alert added in ChiroTouch syncs in real time, with the author resolved to a user name.

• Adit → EHR: three sources write alerts every 15 minutes:

Source | Written as | How the patient is matched
SMS logs | Note (not an alert) | Exact mobile number; written to every patient sharing that number
Follow-ups | Note | Adit patient id mapped to the EHR id
Patient-form allergies, problems, medications | Alert | Skipped if the text already exists

Appointment Sync

Real-Time Appointment Synchronization (ChiroTouch Scheduler → Adit)

Appointment actions in the ChiroTouch scheduler sync to Adit in near real time through the Adit Chrome Extension : create, reschedule, arrived, return-to-scheduled, confirm and unconfirm, no-show, check-in, check-out, cancel, delete and delete-series.

Key Points:

• Real-time sync works only on workstations where the extension is installed and active , with ChiroTouch open and logged in.

• If the extension is not installed , appointment changes are not synced: backup sync is currently disabled, so nothing picks them up later.

• Only appointments at the mapped EHR location are sent. Deletes have no location check .

• Each appointment is enriched with appointment detail, patient summary and encounter charges (2-4 extra EHR calls, 250 ms apart).

• Recurring appointments: each occurrence uses a composite id ( {recurrenceEventId}-{index} ), and a recurring change re-syncs all of the patient's past and future appointments.

Blockouts

• EHR → Adit (real time): when a blocked-off time is created, edited or deleted, the extension re-reads that day's calendar for every provider and room and sends the blockouts (2 attempts per chunk). Series deletes are supported.

Adit Pay (Payments → ChiroTouch Ledger)

Adit Pay payments, discounts and refunds are written into the ChiroTouch ledger through two paths:

• Desktop poll (every 15 minutes): up to 20 pending payments per run.

What gets written depends on the practice's Adit Pay log setting (or the CareCredit financing setting):

Setting | Written to ChiroTouch
1 | Note only (an alert: MM/DD/YYYY - {template} )
2 | Ledger only
3 | Both

Ledger rules:

• Optional discount first, then the payment; refunds post as refund payments.

• Amount in cents. Payment method: cash → Cash, card → Debit or Credit Card, check → Check, otherwise Cash. Transaction date in UTC.

• Provider is taken from the patient's latest past appointment, then the preferred provider, then the first active user, so a payment can be credited to an unrelated provider.

• Already-posted transactions are remembered locally, so a redelivery only re-sends the status.

• Status is reported back to Adit (one retry after 10 seconds). A notes-only sync is wrongly reported as error even when it succeeds.

Documents (Patient Forms → ChiroTouch)

Every 15 minutes the desktop app processes submitted patient forms:

• Create the patient if it has no EHR id, or update the existing patient (form values win).

• Update insurance, emergency contacts and alerts (allergies, problems, medications).

• Export the form PDF from Adit (3 attempts) and upload it to the patient's documents in ChiroTouch.

• Mark the form importing , then completed in Adit.

Known issues: the form is marked completed even if the upload fails , and the folder tag is calculated but not sent, so PDFs land without a folder. Treatment-plan PDFs are disabled.

Most important issues for Support/QA

I would categorize the issues into 6 major buckets:

1. Extension / EHR session issues Real-time sync needs the extension installed, logged in, on the right location, and an open, logged-in ChiroTouch tab. A closed tab or an expired ChiroTouch login stops sync. The badge turns red or yellow when a session is missing.

2. No backup sync Backup sync, deletion reconciliation and the audit-log scraper are disabled . Anything missed by real-time sync stays missing until the record is re-saved in ChiroTouch or Adit requests a manual patient sync. There is no bulk resync.

3. Silent failures and false statuses There is no retry queue: failed appointment, payment and form items are stored locally and never replayed. Some statuses are wrong: forms show completed even when the PDF upload failed, notes-only Adit Pay shows error on success, and approved patients can be acknowledged when the EHR create failed.

4. Duplicates and mismatches Every browser with the extension sends events (no workstation gate). Patients are matched by name + MRN, SMS notes go to every patient sharing a phone, the same appointment can be posted from both the provider and room views, and Adit-created patients have no duplicate check and get a generated 6-character MRN.

5. Desktop app health (Adit → EHR) Payments, forms, confirmations, SMS and follow-ups depend on the desktop app. It can stall on a Cognito MFA prompt , an expired Adit token, or one bad SMS / follow-up item that blocks its batch every 15 minutes.

6. Not synced on this build Master data, practice analytics, recalls, OS v3 online booking writeback, treatment-plan PDFs and deletions found only in the audit log. Clinical data, prescriptions, referrals and claims have no ChiroTouch code.

Where to look when sync fails

• Extension badge and popup: red or yellow means the EHR or Adit session is missing.

• Extension service-worker console (chrome://extensions → Inspect): MESSAGES.* errors, "⚠️ N chunks. Saved in storage for retry.", "nchan: this browser is not the active workstation", "❌ Error in handleAditPayEvent".

• ChiroTouch page console: [XHR.send] lines; scraper step logs.

• Desktop app stdout: "next run in …" scheduler lines, auth errors, PA getTransactionData errors.

• Google Chat channels: aditpay, OS, pf, patientPF, antoC, paProgress, txnV3.

• Adit-side status: payments stuck in error, forms stuck in importing, SMS still pending, follow-ups not confirmed.

Manual recovery

• Adit-initiated manual patient sync re-pulls one patient.

• Re-saving the record in the ChiroTouch UI re-triggers capture.

• No bulk resync is available while the backup jobs are disabled.

Sync issue reported → Check extension badge and location → Check ChiroTouch tab is open and logged in → Check affected workstation (extension installed? primary workstation for payments?) → Check desktop app is running (Adit → EHR) → Check Google Chat channels and failure stores → Check whether the module is disabled on this build → Validate the specific record and re-save or run manual patient sync

Error handling

No dead-letter queue and no metrics. Observability is console logs (EHR page, extension service worker, desktop Node process), Google Chat webhook posts, and a few status acknowledgements to Adit. Failures are mostly logged and skipped; the next poll or event is the recovery mechanism.

• Per-controller try/catch: one failed module does not stop the chain.

• Per-item try/catch: Adit Pay, PF and OS v3. SMS and follow-up pollers have none, so one bad item aborts the batch.

• Timeouts: desktop 60 s idle and 64 MB cap; extension none; audit scraper 60 s overall with 10 s and 30 s element waits.

Where | Retry policy
Desktop EHR GETs | 3 attempts on 5xx, 408, 429 and network errors; 500 ms × 2^n, 8 s cap, jitter
Blockout and PA chunks | 2 attempts; PA then item by item
Txn v3 | 3 per call; postWithRetry 3, then item by item
Adit Pay status ack | One retry after 10 s
PF PDF export | 3 attempts, 2 s × attempt
OS v3 guardian | Up to 10 delayed attempts (~150 s), then a 10-min queue up to 4 h
Socket | Reconnect from 5 s, cap 60 s
Everything else | No retry; un-acked Adit items re-pulled next poll
